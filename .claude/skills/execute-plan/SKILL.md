# Execute Plan Command

<role>Pure execution orchestrator - validates prerequisites then directly orchestrates sub-agent delegation</role>

<mission>Select plan → Verify branch → Verify checklist → Reconcile state → Mark ticket In Progress → Orchestrate execution by spawning sub-agents via the Task tool</mission>

This command executes implementation plans by loading the corresponding checklist and orchestrating sub-agent delegation **directly in this session**. The checklist must already exist (created by `/create-plan`).

**CRITICAL**: This skill spawns all sub-agents itself using the `Task` tool. Sub-agents cannot spawn other sub-agents, so the orchestration logic must live here in the top-level session — not in a delegated agent.

<prerequisites>
  <prerequisite>Plan file exists in context/plans/ (or ad-hoc location)</prerequisite>
  <prerequisite>Checklist file exists in context/checklists/ (generated by /create-plan)</prerequisite>
  <prerequisite>Currently on a feature branch (NOT main)</prerequisite>
</prerequisites>

---

## Stage 1: Plan Selection

**If a plan parameter was provided:**

- Accept either a filename (e.g., `agents-migration-mapping.md`) or full path
- Support both `context/plans/` and ad-hoc plan files
- Verify the plan file exists
- If not found, list available plans and exit

**If no plan parameter was provided:**

- List all plans in `context/plans/` as a numbered list:

  ```
  Available implementation plans:
  1. context/plans/2026-01-26-feature-name.md
  2. context/plans/2026-01-25-another-feature.md

  Or provide a custom plan file path.

  Please enter the number or provide a file path:
  ```

- Wait for user selection, validate it

**After plan is selected:**

- Display plan name, ask for confirmation:

  ```
  You selected: [plan-name]

  Is this the correct plan? (yes/no)
  ```

- If "no" → restart selection. If "yes" → proceed.

## Stage 2: Branch Verification

```bash
git branch --show-current
```

**If on main:**

```
⚠️  You are currently on the main branch.

Please create a new branch before executing the plan:
git checkout -b feature/descriptive-branch-name

Then run this command again.
```

Stop. Do not proceed.

**If on a feature branch:**

The convention is **branch name = plan name** (plan `2026-06-12-webhook-retry.md` → branch `2026-06-12-webhook-retry` or `feature/2026-06-12-webhook-retry`). This lets `/review-execution` and CI pipelines later resolve branch → plan → checklist automatically.

- Derive the plan slug (plan filename without `.md`) and the branch slug (branch name with any leading workflow prefix stripped: `feature/`, `feat/`, `fix/`, `bugfix/`, `hotfix/`, `chore/`, `refactor/`, `docs/`).
- **If the branch slug equals the plan slug** → proceed (recommended setup).
- **If they differ**, warn and recommend renaming so downstream review tooling can match it:

  ```
  ⚠️  Current branch: [branch-name]
  ⚠️  Plan: [plan-slug]

  The branch name doesn't match the plan name. The convention is `branch = plan name`
  so /review-execution can later resolve the checklist from the branch automatically.

  Recommended:
  git branch -m feature/[plan-slug]

  Continue anyway? (yes/no)
  ```

- "no" → exit. "yes" → proceed (the reviewer will fall back to most-recent resolution).

## Stage 3: Checklist Verification

Check for the corresponding checklist:

```
Expected: context/checklists/[plan-name]-checklist.md
```

**If exists** → proceed.

**If missing:**

```
⚠️  No checklist found for this plan.

Expected: context/checklists/[plan-name]-checklist.md

Please run `/create-plan` first to generate the plan and checklist.
```

Exit.

## Stage 3.5: Checklist Reconciliation (MANDATORY on every run)

Before executing any tasks, reconcile the checklist against actual file state. This prevents duplicate work and fixes stale state left by prior sessions.

**For each task marked `[ ]` in the checklist:**

1. Check whether the task's expected output files already exist on disk (use the task's **Files** field).
2. If the files exist and the task has clearly been completed (entity written, migration present, component created), mark the task complete immediately:

```typescript
Edit({
  file_path: 'context/checklists/[checklist].md',
  old_string: '- [ ] **Task X.x**: [title]\n  - **Files**: ...\n  ...\n  - **Status**: Pending',
  new_string: '- [x] **Task X.x**: [title]\n  - **Files**: ...\n  ...\n  - **Status**: ✅ Complete (reconciled — files found on disk)',
});
```

3. After reconciliation, re-read the checklist and identify the **first incomplete task** as the execution entry point. Do not re-run completed tasks.

**Report reconciliation results before proceeding:**

```
Reconciliation complete.

Previously completed (found on disk):
- Task 1.1 ✅ user.entity.ts
- Task 2.3 ✅ user.service.ts (createUser present)

Resuming from: Task 2.4
```

## Stage 3.7: Mark Ticket In Progress (before any task runs)

Executing a plan means work has started, so the linked issue should move to **In Progress** before spawning any sub-agent. You (the orchestrator) do this directly; it is never delegated. This corresponds to **Task 0.1** in the checklist when present.

**Steps:**

1. **Find the ticket ref.** Read the checklist header line (e.g. `**Ticket**: [#NNN](url)`). The URL identifies the provider and project.
2. **No ticket yet?** If the ref is `TBD` or absent, skip gracefully:

   ```
   ℹ️  No ticket linked yet (TBD) — skipping "In Progress" marking.
       Create one with /create-ticket to enable ticket-state tracking.
   ```

   Mark Task 0.1 `✅ Skipped (no ticket linked)` and proceed.

3. **Read current state first** (provider MCP tool or CLI — `gh issue view` / `glab issue view`) so you don't clobber existing labels.
4. **Already In Progress?** Report and continue — no write.
5. **Apply the state**, preserving all other labels; swap any existing `State::*`/status label rather than appending a second one.
6. **Tick Task 0.1** in the checklist (checkbox + Status in one edit, per Step 4.8).

If the provider call fails (auth, network, unknown project), report the error but **DO NOT block execution** — mark Task 0.1 `⚠️ Failed (see note)` and continue. Ticket state is tracking metadata, not a hard gate.

## Stage 4: Execute — Orchestrate Directly

Once stages 1-3 pass, you are the orchestrator. Execute the workflow below yourself, using the `Task` tool to delegate coding tasks to specialized agents.

### Step 4.1: Load Checklist + Handoff

Capture the baseline commit first — you compare against it after every sub-agent returns to catch unauthorized commits:

```bash
git log --oneline -1   # record this SHA as RUN_BASELINE_SHA
```

Read the checklist file:

```typescript
Read({ file_path: 'context/checklists/[plan-name]-checklist.md' });
```

Check for a matching handoff in `context/handoffs/` and load it if present. Store its content — inject it into every sub-agent prompt.

Extract from checklist:

- Agent registry (which agents are assigned)
- Phases and their tasks
- Each task's assigned agent, required skills, dependencies, files, validation commands

### Step 4.2: Load Project Standards

Based on target apps in the checklist, read the relevant `CLAUDE.md` files (root and per-app). Use these as context when prompting sub-agents.

### Step 4.3: Execute Phases Sequentially

For each phase:

```
Phase Start: [Phase Name]
├── Task X.1 → Task(...) call
├── Task X.2 → Task(...) call  (respecting dependencies)
├── Run automated validation (tests/lint/build)
├── Update checklist progress
└── Report phase result → continue straight to the next phase
```

**No manual verification gate.** Automated validation (tests + lint + build) IS the phase gate. Green → proceed immediately to the next phase without asking the developer. Red → the Step 4.6 failure protocol applies (fix, then proceed).

**Phase start communication:**

```
Starting Phase X: [Phase Name]

Tasks to execute:
1. Task X.1 → [assigned-agent]
2. Task X.2 → [assigned-agent]

Beginning execution...
```

### Step 4.4: Delegate Tasks via Agent Tool

For each task, call the `Task` tool:

```typescript
Task({
  subagent_type: '[assigned-agent-from-checklist]',
  description: '[brief task description]',
  prompt: `Execute this task:

**Task**: [task description from checklist]

**Files**: [files from checklist]

**REQUIRED SKILLS — load these BEFORE writing any code**:
Call \`Skill({ skill: '<name>' })\` for EACH of: [skills from checklist]
These encode this project's rules and OVERRIDE your defaults. Reading the names is
not enough — you must invoke each one. If a skill name does not resolve, report it
instead of guessing. If the checklist lists no skills, omit this block.

**Handoff Context** (decisions, constraints, discoveries from prior sessions):
[paste full handoff content here — omit if no handoff was loaded]

**Context**:
- Target app: [from checklist]
- Previous task output: [if dependency exists]
- Project standards: [relevant standards from CLAUDE.md]

**Requirements**:
- Follow all coding standards
- Use Write/Edit tools for file operations (NEVER cat or echo)
- Report files modified and any interfaces created

**HARD PROHIBITIONS — violating any of these fails the task**:
- NEVER run any git command that mutates state: no \`git add\`, \`commit\`, \`push\`,
  \`checkout\`, \`switch\`, \`branch\`, \`merge\`, \`rebase\`, \`reset\`, \`stash\`, \`tag\`.
  Read-only inspection (\`git status\`, \`git diff\`, \`git log\`) is fine. The
  orchestrator owns all version control. Leave your changes uncommitted in the
  working tree.
- NEVER edit the checklist under \`context/checklists/\`. The orchestrator owns it.
- NEVER edit any plan under \`context/plans/\` or any review under \`context/reviews/\`.
- Touch ONLY the files this task names, plus files you must change to make them
  compile. Anything else is scope creep — report it instead of doing it.

**Success criteria**:
[from checklist]`,
});
```

**Why skills must be an explicit instruction, not a label:** the same reasoning as the git prohibition below. A checklist line reading `**Skills**: security-patterns` sends the sub-agent the *word* "security-patterns" — no content, no file. The agent then substitutes its own priors for the project rule the skill encodes, and nothing surfaces the difference. Sub-agents carry `Skill` in their tool allowlist for exactly this; the prompt has to tell them to use it.

**Why the git prohibition is in the prompt, not just the Constraints section:** sub-agents only read the prompt you send them. A rule that lives only in this skill is invisible to them — sub-agents have been observed auto-committing **and pushing** unprompted. Include the prohibition block verbatim in **every** delegated prompt.

**For parallel tasks (no dependencies between them)** — make all Task calls in a **single message**:

```typescript
// ✅ CORRECT — one message, parallel execution
Task({ subagent_type: 'ui-builder', description: '...', prompt: '...' });
Task({ subagent_type: 'nestjs-developer', description: '...', prompt: '...' });

// ❌ WRONG — separate messages = sequential execution
```

**For sequential tasks with dependencies** — wait for the previous sub-agent to complete before sending the next one, then pass its output as context.

### Step 4.5: Agent Selection

**The checklist's `**Assigned Agent**` is authoritative.** Pass it to `subagent_type`
verbatim. Do NOT substitute a different agent because it feels closer, more familiar, or
appears in the fallback table below — that table is ONLY for tasks with no assignment. If
you believe an assignment is wrong, say so and ask; never silently reroute.

**Before the first delegation**, confirm every distinct assigned agent exists:

```typescript
Glob({ pattern: '.claude/agents/*.md' });
```

If an assigned agent has no file, STOP and report which task names it. A non-existent
`subagent_type` fails the call outright — it does not fall back to anything.

Keep the fallback table and tier order below in sync with the agents actually installed.
An agent that `checklist-generator` can assign but this list omits is how a specialized
agent gets assigned repeatedly and invoked never: the orchestrator reads the list, does
not find it, and quietly drops to a generic fallback.

**Only when a task has no assigned agent**, pick by target area:

| Target app                | Fallback agent      |
| ------------------------- | ------------------- |
| `apps/server/src` backend (Nakama runtime) | `general-purpose` |
| `packages/rules/src` rules engine / bots | `general-purpose` |
| `apps/mobile/src` frontend (Expo) | `general-purpose` |
| Any                       | `code-refactor`     |

**Tier order for unassigned tasks only** (prefer specialized over generic):

1. Specialists: `test-specialist`, `debug-specialist`, `ui-prototyper`, `docs-maintainer`, `code-refactor`
2. Fallback (last resort): `general-purpose`

### Step 4.6: Run Tests After Each Phase (MANDATORY — BLOCKING)

After all tasks in a phase complete, run tests before proceeding:

```bash
pnpm test
```

**Test failure protocol:**

1. DO NOT proceed to the next phase
2. Delegate to `debug-specialist` (runtime errors) or `test-specialist` (test code issues) via Task tool
3. Re-run until all pass
4. Only then proceed

**Report format:**

```
Phase X - Test Results:
✓ Tests: 45/45 passed (0 failed)
✓ Lint: No issues
✓ Build: Succeeded

Proceeding to documentation task...
```

### Step 4.7: Write Phase Documentation

After each phase, write docs while context is fresh:

```typescript
// First phase — create the file
Write({
  file_path: 'context/docs/[plan-name]-docs.md',
  content: `# Documentation: [Plan Name]\n\n## Phase 1: [Phase Name]\n\n### Changes Made\n...\n\n---\n`,
});

// Subsequent phases — append
Edit({
  file_path: 'context/docs/[plan-name]-docs.md',
  old_string: '---\n',
  new_string: `---\n\n## Phase N: [Phase Name]\n\n### Changes Made\n...\n\n---\n`,
});
```

**After ALL phases complete**, delegate to `docs-maintainer` to merge into permanent docs:

```typescript
Task({
  subagent_type: 'docs-maintainer',
  description: 'Merge temp docs to permanent Diataxis docs',
  prompt: `Merge temporary documentation into permanent Diataxis docs.

**Source**: context/docs/[plan-name]-docs.md (TEMPORARY — delete after merge)
**Target**: docs/ (permanent Diataxis structure)

Steps:
1. Read the accumulated docs from context/docs/[plan-name]-docs.md
2. Classify each section by Diataxis type (explanation, how-to, reference, tutorial)
3. Create or update files under docs/{diataxis-type}/
4. Delete the temporary context/docs/[plan-name]-docs.md file

IMPORTANT: context/docs/ is temporary staging only. Final docs MUST live under docs/.`,
});
```

### Step 4.8: Update Checklist Progress (HARD GATE — no exceptions)

**THE SINGLE INVIOLABLE RULE: update the checklist BEFORE doing anything else after an agent returns. No next tool call, no next message, no test run — update the checklist first.**

This is not a "best effort" step. If you skip or defer it, checklist state drifts and future sessions cannot resume correctly.

**The orchestrator (you) owns the checklist. Sub-agents MUST NOT edit it. Ever.**

After each `Task()` call returns, immediately edit BOTH the checkbox AND the Status field in a single `Edit` call:

```typescript
Edit({
  file_path: 'context/checklists/[checklist].md',
  old_string: `- [ ] **Task X.1**: [exact title]
  - **Files**: [files]
  - **Assigned Agent**: [agent]
  - **Skills**: [skills]
  - **Dependencies**: [deps]
  - **Validation**: [validation]
  - **Status**: Pending`,
  new_string: `- [x] **Task X.1**: [exact title]
  - **Files**: [files modified — list actual files touched]
  - **Assigned Agent**: [agent]
  - **Skills**: [skills]
  - **Dependencies**: [deps]
  - **Validation**: [result]
  - **Status**: ✅ Complete`,
});
```

**If the `Edit` fails** (old_string mismatch because the file changed externally): read the checklist fresh, find the task, retry. Do not proceed until the checklist reflects reality.

**Failure mode to avoid:** updating only the checkbox `[ ] → [x]` but leaving `Status: Pending`. Both must change in one edit.

### Step 4.9: Report Phase Result and Continue (NO manual gate)

Phases are gated by **automated verification only**. Once lint, tests, and build are green for a phase, report and move straight into the next phase — never stop to ask the developer to eyeball anything.

After each phase:

```
Phase X Complete! ✓

**Tasks Completed:**
- Task X.1: [description] — agent: [agent-name]
- Task X.2: [description] — agent: [agent-name]

**Automated Verification:**
✓ Lint passed
✓ Tests passed (45/45)
✓ Build succeeded

Proceeding to Phase X+1...
```

**Manual verification steps in the checklist** are not a blocking gate. Handle them like this:

1. If the step can be automated cheaply, automate it instead of asking:
   - Behaviour/regression → have `test-specialist` add or extend a test.
   - UI/visual → delegate to `ui-explorer` to drive the live app and report.
   - HTTP/endpoint → curl the running local service and assert the response.
2. If it genuinely cannot be automated (needs a real third-party account, a payment, a physical device, production data), do NOT stop. Record it under a `## Deferred Manual Verification` section in `context/docs/[plan-name]-docs.md` with the exact steps, and keep going.
3. Surface all deferred items once, in the final completion summary at the end of the run — not at each phase boundary.

**Only halt mid-run for:** unrecoverable validation failure (Step 4.6 protocol exhausted), a repeatedly failing agent (Error Handling), or a missing dependency that cannot be resolved. Nothing else stops the run.

### Step 4.10: Final Summary

When all phases are complete, report:

- Phases/tasks completed, agents used
- Final validation results
- Any `## Deferred Manual Verification` items, listed in full
- Next step: **run `/review-execution` before committing.**

## Error Handling

**Agent fails:**

1. Document failure in checklist
2. Report: which agent, what task, error context
3. Wait for guidance (retry, skip, or abort)

**Validation fails:**

1. DO NOT proceed
2. Delegate to `debug-specialist` (runtime errors) or `test-specialist` (test code issues)
3. After 2 failed attempts → report to developer, document in checklist, wait for guidance

**Dependency missing:**

1. Identify which previous task output is needed
2. Execute the dependency task first if not yet done

## Constraints

- NEVER execute on main branch
- NEVER skip checklist or branch verification
- ALWAYS reconcile the checklist against disk (Stage 3.5) before executing any task
- ALWAYS attempt to mark the linked ticket In Progress (Stage 3.7) — skip gracefully when none is linked, and never let a provider failure block execution
- NEVER write application code yourself — delegate ALL coding tasks via Task tool
- NEVER use cat/echo for file operations — always use Write/Edit tools
- ALWAYS run tests after every phase before proceeding
- NEVER wait for developer confirmation at a phase boundary — green automated validation IS the gate; run every phase to completion unattended
- NEVER stop for a checklist "manual verification" step — automate it (test / `ui-explorer` / curl) or defer it to the final summary
- The ONLY files you modify directly: the checklist (progress tracking) and context/docs/ (phase documentation)
- **NEVER instruct sub-agents to update the checklist.** Sub-agents touch only application code. The orchestrator (you) owns all checklist edits.
- **ALWAYS include the HARD PROHIBITIONS block (Step 4.4) verbatim in every delegated prompt** — no git mutations, no checklist/plan/review edits, no scope creep. Sub-agents cannot see this Constraints section.
- **After each sub-agent returns, verify it did not commit:** run `git log --oneline -1` and compare against `RUN_BASELINE_SHA`. If a sub-agent committed anyway, report it immediately — do not silently continue.
- **The orchestrator does not commit during a run.** Committing is the developer's call after `/review-execution`. If explicitly asked to commit, stage with **explicit pathspecs** (`git commit -- <file> <file>`) — never `git add -A`/`git add .`, because concurrent sessions' hooks can stage other files into the shared index.
- **ALWAYS update the checklist immediately after each agent returns** — before tests, before the next agent call, before anything. This is the single most important constraint across sessions.
