Players directory & player profile

A display name is now a player's unique, public handle, so the random friend code leaves the UI. This is the page that makes names findable: search a name, see who is around, open a profile with stats and the friend actions. It reuses the Café Tunisien skin, the friends screen's availability states and the existing destructive-confirm sheet. Phone is the primary case; switch width and language above. Try typing am, clicking Add friend, then clicking Request sent, and opening the overflow menu on a friend.

What this prototype covers

  • Directory: recent players before typing, a 2-character gate, a loading skeleton, results, and a no-results state with a way back. The Players / Ranking switch leaves room for ranking later.
  • Profile: large avatar, availability, relationship line, sample stats, and actions for Add friend, Request sent, Friends, Remove friend and Blocked. Block and Remove use the app's confirm sheet.
  • Friends entry point: one "Find players" card at the top of the friends screen; the lists below are untouched.
  • Both widths and both languages. Phone first; desktop keeps the list and puts the profile in a side panel. Derja is a real dir="rtl" variant, not mirrored text.

Design decisions and tensions

  • No codes anywhere. The current friends screen also has a code card and "Add by code"; those would have to go when the code retires. The inset deliberately shows only the new entry point and the lists, so it does not redesign that screen here.
  • Availability colours are the skin's. Online is the token's green, in a room and in a game share the gold accent (as availabilityColor does today), offline is the muted brown. The label carries the room/game difference.
  • Search starts with the name, not a substring. Names are unique, so a prefix search can still return one row per name; the result count stays honest. Diacritics are folded (hedi finds Hédi).
  • Desktop is an adaptation, not a second design. Tapping a row fills the right panel instead of pushing a screen. That matches how the friends screen already uses two columns at 900 px and wider.
  • Invite is only for online friends. An offline friend still has a profile; the invite button is disabled with the reason.

Prototype shortcuts

  • Search latency is simulated (about half a second) so the skeleton is visible; results are local sample data.
  • In the directory, tapping Add friend sends the request; tapping Request sent simulates the other player accepting, so you can reach Friends. The profile frame's tools jump straight to any state.
  • Stats are clearly fictional sample numbers (128 / 73 / 41 / 9) and sit in a layout that can take more rows later.
  • The page is HTML, CSS and one sibling script (chkobba-users-app.js), with no framework and no build step. Fonts come from the repo's local @expo-google-fonts packages, so nothing is fetched over the network. Under file:// some browsers block local font files; serve the repo root and open /context/ui/chkobba-users.html for exact type.

Questions this exposes

  • Should blocking also hide a player from directory search, or only from your lists and tables? The prototype leaves them findable but labelled Blocked.
  • Does prefix search match what players expect? An exact-name search is stricter; prefix lets "ami" find Amira, which may be fine because names are unique.
  • What counts in "Games played" and "Wins": 2v2 only, or 1v1 too? Separate tabs would need room in the stats block.
  • Should the unlisted callout also appear on the friends screen, where players are most likely to wonder why nobody finds them?
  • Can an unlisted player be invited to a table they were never at? This prototype assumes yes via the existing friends list.
