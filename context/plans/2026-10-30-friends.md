# Plan: Friends v1 (friend codes, requests, recent players, presence, table invites)

**Status:** CONFIRMED (developer, 2026-10-30)
**CONFIRMED:** true
**Base branch:** the private-tables branch (`context/plans/2026-10-30-private-tables.md`). Private tables is implemented first; this plan starts from it.

**Goal:**

- Every online player has a friend code (their Nakama username, shown `XXXX-XXXX`) and a share link `/f/CODE`.
- Players add friends from the table, from a recent players list, or by code or link. Requests can be accepted, declined or cancelled; friends can be removed; anyone can be blocked and unblocked.
- The friend list shows who is online, in a game, or offline.
- From a private table's waiting room, a player invites an online friend; the friend gets an in-app invite carrying the room code and joins with one tap.

## Prerequisite: private tables

This plan branches from the private-tables branch.

- **Phases 0 to 5** reuse `ROOM_CODE_ALPHABET` (`packages/protocol/src/room.ts`), the share-link helper (`EXPO_PUBLIC_WEB_BASE_URL`), and the shared `NameGate` extracted from `FindingPlayers`.
- **Phase 6** (invites) requires `create_private_table`, `join_by_code`, the `private_table` code mapping, room `members`, and the `/t/[code]` route.

## Decisions (developer, 2026-10-30, not re-opened)

- Nakama's built-in friends: states 0 mutual, 1 sent, 2 received, 3 blocked; `addFriends`, `listFriends`, `deleteFriends`, `blockFriends`; Nakama's own notifications for requests and accepts. No SQL.
- Discovery v1: "Add friend" on human players at your table, a recent players list, and a friend code with a share link. No search by display name.
- Friend code = the Nakama username: 8 characters from the room-code alphabet (no `0`, `O`, `1`, `I`), displayed `XXXX-XXXX`. Add by code uses Nakama add-by-username. The `Guest-XXXX` generator and its Nakama-random fallback go away. Dev accounts are reset; no migration. Usernames stay locked (`apps/server/src/account/hooks.ts:44`). The share link reuses the private-tables web link scheme: `${EXPO_PUBLIC_WEB_BASE_URL}/f/CODE`.
- Limits: a server before-AddFriends hook caps outgoing pending requests at 50 and the friend list at 200. Declines and cancels are silent. Mutual add = friends. Hooks follow CLAUDE.md conventions (return `data`; throw `{ message, code }` with numeric codes).
- Presence: the client sets its status over the socket (online, at a table) and follows its friends' statuses; the list shows availability.
- Invites to a private table: an in-app notification carrying the table code.
- Block is required (store compliance). A blocked player can't re-request and is hidden from recent players.
- Facebook friend import: out of scope (Facebook login step).
- All UI text in `en` and `aeb`. Wire types in `@chkobba/protocol`, additive only. Server module goja-safe (ES5 bundle, ES2017 lib).

### Resolved questions (developer, 2026-10-30)

1. **The server generates the friend code** in a `beforeAuthenticateDevice` hook. An early check confirms the before hook can rewrite `username`. Fallback if it can't: the server rejects a missing or malformed code, and the client retries with a client-generated candidate.
2. **User ids at the table:** optional `PlayerInfo.userId` on human seats, and `RoomMember.userId` in Phase 6.
3. **Name gate:** sending a request, accepting and inviting require a picked name, through the shared `NameGate`. Browsing friends and viewing your code need no name.
4. **Recent players:** recorded at game finish for everyone still seated, and for a player who leaves mid-game at the moment they leave. Both lists include every human who sat in that game, leavers included. Best effort, never fails `matchLoop`. Once per game per player, also for multi-game private tables.
5. **Invites during a game:** a quiet badge during a hand. A banner with Join on lobby screens, or when their game ends if the invite hasn't expired.
6. **Social socket:** connects at launch only if a stored session exists, otherwise on first Friends or online use. Disconnects in the background, reconnects on foreground.
7. **Invite limits:** 20 per sender per 10 minutes; invites expire after 10 minutes (`INVITE_TTL_MS`); at most one pending invite per (sender, friend, table), and repeats are no-ops.

### Technical decisions (mine; revisit at review)

1. **Server-generated friend code.** The `beforeAuthenticateDevice` hook replaces a missing or malformed `username` with a fresh code: a pure generator over `nk.uuidv4()` bytes, screened with the server profanity list and checked with `nk.usersGetUsername`. The client sends no username. A client could otherwise pick a vanity or offensive name, which is now user-visible, and the profanity list stays server-only. Old builds sending `Guest-XXXX` still sign in: the hook overwrites it on create, and Nakama ignores it for existing accounts. The client keeps one retry on 409; the hook picks a new code on each call.
2. **A separate, app-level "social socket".** `NakamaGameClient` keeps its own per-game socket, with `createStatus: false`, unchanged. A new shared `SocialSocket` connects with `appearOnline: true`, owns the status, follows friends and receives notifications. Two sockets per user are allowed: the local Nakama config has no `single_socket`. Connection timing follows resolved question 6, so opening the app for offline play never creates an account.
3. **Status carries availability only, never a code or match id.** Any user can follow any user id, so the status is public. The format is a small JSON `PresenceStatus`: `lobby`, `room` or `playing`. Invites are the only path to a private table code.
4. **User ids at the table** come through the optional `PlayerInfo.userId`. Old decoders rebuild snapshots from known fields only, so they drop it. Friend actions use the standard add-by-id.
5. **The adapter records recent players,** not the pure core.
   - It keeps a per-game roster in match state: every human who held a seat since the game started, including private-table takeovers.
   - When `matchLeave` releases a seated human while a game runs (disconnect or leave), it writes that player's record from the roster as it stands.
   - When the phase moves to `finished`, it writes a record for every roster member who hasn't been written for this game yet.
   - A per-player guard keyed by the game makes each player's record update happen at most once per game. A leaver who reconnects isn't written again at finish.
   - The roster and the guards reset when a new game starts (private `gameNo`).
   - Writes are best effort: try/catch, logged, never fail the loop. The record keeps the last 20 tables. The client dedupes players and refreshes names with `getUsers`.
   - Known gap: a leaver's entry lacks players who sat down after they left.
6. **The before-AddFriends hook classifies each target** against the caller's own edges (`nk.friendsList`, up to 1000 per state):
   - A target in state 2 is an accept, and counts toward 200 for both users.
   - A target in state 0 or 1 is a no-op.
   - A target with no edge is a new request, and counts toward the 50 outgoing.
   - Usernames are resolved with `nk.usersGetUsername`. The hook caps targets per request at 10 and drops the caller's own id.
   - Blocked targets rely on Nakama's native behaviour: a block deletes the other side's edge and silently ignores a re-request. Phase 2 verifies this, and the hook filters blocked targets only if Nakama doesn't.
7. **An invite is an RPC plus a persistent notification.**
   - `invite_to_table` checks that the caller is authenticated and within the rate limit, is a mutual friend of the target, and is a present member of the private table with that code.
   - Membership is asked of the live match through `nk.matchSignal`.
   - A repeat for the same (sender, friend, table) within `INVITE_TTL_MS` returns success without sending.
   - It sends with a positive custom notification code; Nakama reserves negative codes.
   - The client shows an invite older than `INVITE_TTL_MS` as expired, and `join_by_code` is the final liveness check.
8. **Friend state is the source of truth; notifications are triggers.** Badges and lists come from `listFriends`. A `-2`, `-3` or invite notification only refreshes the list and shows a toast. Seen notifications are deleted, so a cancelled request leaves no ghost.

## Current state (key discoveries)

**Identity and auth (mobile)**

- `guestUsername` builds `Guest-` plus 4 symbols from `USERNAME_ALPHABET`, the same 32-symbol alphabet as room codes (`apps/mobile/src/online/nakama.ts:97-112`).
- `GuestAuth.authenticate` tries two generated usernames, then `undefined` (Nakama picks one) on 409 (`nakama.ts:319-333`).
- `openSocket` creates a socket per call and connects with `createStatus: false` (`nakama.ts:466-485`). Only `NakamaGameClient` uses it. Nothing holds a long-lived socket or handles notifications or status.
- Shared singletons: one `Client`, one `GuestAuth`, one `OnlineBackend` and one `ProfileBackend` (`apps/mobile/src/online/services.ts`). `ProfileBackend` reads `getAccount` but doesn't expose the username (`apps/mobile/src/online/profile.ts:168-189`).

**Server**

- `InitModule` registers `smoke_game`, `quick_match`, the update-account hooks, `afterAuthenticateDevice` and the match (`apps/server/src/main.ts:45-63`). It has no before-auth or friend hooks.
- `beforeUpdateAccount` already rejects username changes with `username_locked` (`apps/server/src/account/hooks.ts:44`).
- `afterAuthenticateDevice` sets the default `PlayerNNNN` display name on create (`hooks.ts:102-121`).
- Error convention: numeric gRPC codes as local consts, thrown as `{ message: <code string>, code }` (`hooks.ts:16-31`).
- Storage patterns:
  - a server-owned per-user record with read 1 and write 0 (`profile/name`, `hooks.ts:82-91`)
  - a system-user versioned record (`apps/server/src/rpc/quickMatch.ts:53-84`)
- Runtime API in nakama-common v1.47.0:
  - `registerBeforeAddFriends`, request `{ ids?, usernames? }`
  - `friendsList(userId, limit, state, cursor)`, `friendsAdd`, `friendsDelete`, `friendsBlock`
  - `notificationSend(userId, subject, content, code, senderId, persistent)`
  - `statusFollow`, `usersGetUsername`, `matchSignal`

**Table and match**

- `HumanSeat` keeps `userId` for the whole game, even while disconnected (`apps/server/src/table/types.ts:28-38`).
- `matchLeave` releases sessions through `leave` (`apps/server/src/match/tableMatch.ts:127-140`, `:298-307`).
- `matchLoop` runs intents, then `advance` and `publish`, then closes on `terminationReason` (`:143-162`). `matchSignal` is a no-op (`:177-187`).
- `PlayerInfo` has `name`, `isBot`, `away` and `connected`, but no user id (`packages/protocol/src/index.ts:47-54`). The mobile decoder rebuilds snapshots from known fields only.

**Lobby**

- The home screen has a "Soon" `tile-friends` (`apps/mobile/src/app/index.tsx:126`) and a header profile chip showing the name and "offline" (`index.tsx:90-98`).
- Sheets use `LobbySheet`, tiles use `LobbyTile`, and icons use `LobbyIcon`, which already has a `friends` icon.

## Desired end state

- **My code:** the friends screen shows my code `K7M2-QX9A` in large type, with Share and Copy. Share sends the `/f/K7M2QX9A` link when `EXPO_PUBLIC_WEB_BASE_URL` is set, and the code alone otherwise. No name is needed to see it.
- **Add by code or link:** typing a code (dashes, spaces and case ignored) or opening `/f/CODE` shows that player's display name with "Add friend".
  - Your own code says "This is your code".
  - An unknown code says "No player with this code".
  - Sending goes through the name gate on the first time.
- **Requests:**
  - Incoming requests show Accept, Decline and Block. Accept goes through the name gate.
  - Outgoing requests show Cancel.
  - The friends tile and screen show an incoming-request badge.
  - Decline and cancel are silent.
- **Limits:** the 51st outgoing request, or the 201st friend, shows a clear localized message.
- **Friends list:** online friends come first. Each shows Online, In a game or Offline, and a row menu has Remove and Block.
- **At the table:** tapping another human's seat offers Add friend (or shows Friends or Request sent) and Block. Blocking at the table also mutes that seat's emotes.
- **Recent players:**
  - Humans from my last 20 tables, each listed once, newest first.
  - It covers games I finished and games I left, with every human who sat in them.
  - Blocked players are not shown.
- **Blocked list:** lists blocked players with Unblock.
- **Invites (Phase 6):**
  - In a private waiting room, "Invite friends" lists online friends with Invite. Inviting the same friend again is a no-op shown as "Invited".
  - The friend sees a quiet badge during a hand. On lobby screens, or when their game ends, they see a banner like "Hedi invites you to a table" with Join, which opens `/t/CODE`.
  - Expired invites show "This table has closed": older than 10 minutes, or the room is gone.
- **Everywhere:** `en` and `aeb`, phone and desktop layouts, skins through tokens and slots. Codes render in an LTR isolate in RTL.

## What we're NOT doing

- Search by display name, friends of friends, contact or Facebook import.
- Chat, direct messages, reporting. CLAUDE.md requires reporting once chat or groups exist, and neither does yet.
- Groups or clans.
- Push notifications (APNs, FCM). Everything is in-app over the socket, plus the persistent notification list on next launch.
- Avoiding blocked players in quick match, or kicking a blocked player from a private table.
- Changing or regenerating a friend code.
- Migrating existing `Guest-XXXX` accounts.
- Inviting to public quick-match tables.
- "Last seen" times, custom status text, appearing offline.
- Deploying the web build or the backend.

## Phase 1: Friend-code usernames

**Goal:** every new account gets a valid, server-generated friend code as its username, and the client can show its own code.

**Tasks**

- **Verify first:** on Nakama 3.40, check that a `registerBeforeAuthenticateDevice` hook can rewrite `username` on a create, and that username lookup case behaves as expected. Record the result in ADR-0003. The rest of the phase follows the path this check picks.
- **Server generator:** a pure friend-code generator that takes a random source. It screens out codes containing a word from `apps/server/src/account/profanity.ts`.
- **Primary path:** the `beforeAuthenticateDevice` hook sets a generated code when `username` is missing or not a valid code.
  - It picks a code that `nk.usersGetUsername` doesn't know, with up to 5 tries, then lets Nakama answer 409.
  - It never rejects a sign-in.
  - Register it in `main.ts` as a top-level named function.
- **Fallback path,** only if the hook can't rewrite `username`:
  - The hook rejects a missing or malformed code with `username_bad_code`. A profanity hit is rejected the same way.
  - The client generates a candidate with the shared `friendCodeFromBytes`, and retries with a new candidate on 409 or `username_bad_code`, up to 3 tries. There is no Nakama-random fallback.
- **Mobile:**
  - Remove `guestUsername` and the Nakama-random fallback from `GuestAuth.authenticate`.
  - On the primary path, send no username and keep one retry on 409.
- **Profile:** `Profile.friendCode` comes from `account.user.username`, and is null when that isn't a valid code. It is cached with the profile.
- **Tests:**
  - the hook: missing, malformed and valid usernames, a clash retry, a profanity skip (or rejections on the fallback path)
  - the generator vectors
  - `GuestAuth` on the chosen path, with no fallback
  - the profile mapping
- **Dev reset:** a note in `docs/how-to/local-backend.md` on wiping the local database so every account has a code.

**Success criteria**

- Server Vitest and mobile Jest pass, and the module loads in goja.
- Manually:
  - a fresh device account's username is an 8-character code
  - `beforeUpdateAccount` still rejects a username change

**Risks**

- **Username case.** Always store and look up the normalized uppercase form.
- **Social login later** creates accounts through other authenticate calls. Each one will need the same before hook; ADR-0003 notes it.
- **Old builds sending `Guest-XXXX`** keep working on the primary path. On the fallback path they can't create new accounts, which is accepted (pre-release, dev accounts reset).

## Phase 2: Server friend rules and recent players

**Goal:** the server enforces request limits, records recent players at game end and when a player leaves, and exposes human user ids at the table.

**Tasks**

- **`registerBeforeAddFriends` hook** in `apps/server/src/social/`:
  - requires an authenticated caller and caps the targets
  - resolves usernames and classifies targets (technical decision 6)
  - enforces the 50 outgoing and 200 friend limits, including the other user's 200 on accept
  - returns `data` with the caller's own id removed
  - throws errors from `FRIEND_ERROR_CODES` with numeric codes
- **Verify block behaviour:** a re-request from a blocked user is ignored, and the blocked user can't see the blocker. Add a filter in the hook only if needed.
- **Recent-player helpers:**
  - a pure `recordRecentTable(record, roster, ownerUserId, endedAt)`: it drops bots and the owner, dedupes, caps at 20 tables and keeps newest first
  - a parser that treats a malformed record as empty
- **Adapter roster:** set `gameKey` and start the roster when a game starts. Append each human who takes a seat during the game, including takeovers. Reset on a new game.
- **Adapter write on leave:** when `matchLeave` releases a seated human while a game runs and they aren't in `recentWritten`, write their record from the current roster and add them to `recentWritten`.
- **Adapter write on finish:** when the phase moves to `finished`, write a record for every roster member not yet in `recentWritten`.
- **Write rules:** read-modify-write on `social/recent_players` with read 1 and write 0, in try/catch with logging. A storage failure never fails `matchJoin`, `matchLeave` or `matchLoop`.
- **Projection:** `PlayerInfo.userId` for human seats.
- **Fakes:** `friendsList`, `friendsAdd`, `friendsBlock`, `usersGetUsername`, `notificationSend` and `matchSignal`, as needed.
- **Vitest:**
  - the hook's classification and each limit boundary, the accept rule counting for both users, malformed requests
  - recent players: bots excluded; a leaver written at leave time with everyone who sat so far; a leaver who reconnects not written twice; players still seated at finish get every roster member, leavers included; the 20-table cap; a second private game recorded separately
  - the projection includes `userId` only for humans
  - a storage failure doesn't break the match handlers

**Success criteria**

- Server Vitest passes, and the module loads in goja.
- Manually, with curl or the console:
  - the 51st pending request is rejected with `friend_outgoing_limit`
  - a finished game leaves a `recent_players` record for each human, and a player who left mid-game has one too

**Risks**

- **Hook cost.** Each AddFriends lists up to 1000 edges per state. With limits of 50 and 200 this stays small.
- **Writes on the leave path** add one storage round trip per departing human. Leaves are rare, so this is acceptable.
- **Concurrent writes to one record** are practically impossible. Last writer wins is accepted, as with `profile/name`.
- **Limit races** between parallel AddFriends calls can overshoot by a few. Accepted.

## Phase 3: Mobile social services

**Goal:** the app has a friends backend and an app-level social socket for presence and notifications. No UI yet.

**Tasks**

- **`FriendsBackend` over nakama-js:**
  - `listFriends` per state, with paging
  - `addFriends` by id, `deleteFriends`, `blockFriends`
  - `getUsers` by username for code lookup
  - `readStorageObjects` for recent players
  - `rpc` for invites
  - Hook errors are mapped from the response body, like `nameErrorFrom`.
- **Recent players:** flatten the tables, dedupe by user (newest wins), drop blocked users, then enrich with current names and friend states.
- **`SocialSocket` connection:**
  - It connects with `appearOnline: true` at launch only if a stored session exists, and otherwise on first Friends or online use.
  - It disconnects when the app goes to the background (AppState, or page visibility on web), and reconnects on foreground and after a network drop, with backoff.
- **`SocialSocket` behaviour:**
  - It sets `PresenceStatus` and follows mutual friends, re-following when the list changes.
  - It maps status presences to `Availability`.
  - It receives notifications, loads the persistent list on connect and deletes seen ones.
- **Activity API:** `setActivity('lobby' | 'room' | 'playing')`, called by the game and room screens. The provider also exposes whether a hand is in progress, so the invite badge and banner logic can use it.
- **`services.ts`:** singletons for `FriendsBackend` and `SocialSocket`, plus a React `SocialProvider` at the root layout that exposes `SocialState` and the actions.
- **Decoder:** pass through `PlayerInfo.userId` when it is a string, and drop it otherwise.
- **Jest:**
  - backend mapping and errors
  - recent-player dedupe and block filtering
  - status encoding and decoding (an unknown or malformed status counts as online)
  - notification handling: request, accept, invite, expired invite
  - connection rules: no socket and no account creation without a stored session; connects on first online use; disconnects in the background and reconnects on foreground

**Success criteria**

- Mobile Jest and typecheck pass.
- Quick match and `LocalGameClient` are unchanged.

**Risks**

- **Two sockets per user.** If `single_socket` is ever enabled server-side, the game socket would kick the social one. ADR-0003 records the dependency.
- **Status follow limits.** Confirm that Nakama has no follow cap below 200 ids.

## Phase 6: Invites to private tables

**Goal:** a player in a private waiting room invites online friends, and an invited friend joins with one tap.

**Tasks**

- **Adapter:** `matchSignal` answers `MemberQuery` with whether the user is a present member of the room.
- **`invite_to_table` RPC:**
  - authenticated
  - validates the id and code
  - checks the caller is a mutual friend of the target
  - looks up the code and checks liveness through the private-tables mapping
  - checks membership through `nk.matchSignal`
  - applies the per-sender window (`INVITE_LIMIT` per `INVITE_WINDOW_MS`) and the per-(friend, code) dedupe in `social/invite_limits`, pruning stale entries
  - a repeat within `INVITE_TTL_MS` returns `{ sent: false }` without sending and without counting toward the limit
  - otherwise it sends a persistent `TABLE_INVITE` notification and returns `{ sent: true }`
  - registered in `main.ts`
- **`RoomMember.userId`** (optional) in the room projection and the decoder, so "Add friend" works on room members too.
- **Room UI:** "Invite friends" opens a sheet of friends with their availability, online and lobby first. Each row has Invite, which shows "Invited" after a send or a repeat. Inviting goes through the `NameGate`.
- **Incoming invites:**
  - During a hand, a quiet badge on the table's menu.
  - On lobby screens, or when the recipient's game ends, a banner if the invite hasn't expired. Join opens `/t/CODE`; Dismiss deletes the notification.
  - Expired invites (older than `INVITE_TTL_MS`, or `room_not_found` on Join) show as closed.
- **Activity:** `setActivity('room')` in the waiting room, and `'playing'` during a game.
- **i18n:** `invite.*` keys in both catalogs.
- **Tests:**
  - Vitest for the RPC: each error, the window boundary, the dedupe no-op and the window after expiry, one notification on success
  - Vitest for `matchSignal` membership
  - Jest and RNTL for the invite sheet, the badge during a hand, the banner after the game, expiry and Join navigation
- **e2e:**
  - A creates a private table and invites B.
  - A second invite is a no-op.
  - B receives one notification, joins by its code and lands in the room.
  - An invite to a non-friend fails with `invite_not_friend`.

**Success criteria**

- Server Vitest, mobile Jest, typecheck, lint and e2e pass.
- Manually, with two browser windows:
  - invite, Join, and land seated in the room
  - an invite received mid-hand shows as a badge, then as a banner after the game
  - an invite after the room closed shows as closed

**Risks**

- **`matchSignal` from an RPC** waits for the match loop (1 Hz tick), so an invite can take up to about 1 s. Acceptable.
- **The dedupe window is per room code.** A new table means a new code, so a friend can be invited again right away.

## Risks (cross-cutting)

- **Status privacy.** Anyone who knows a user id can follow its status. It only reveals lobby, room or playing, never a code.
- **User ids on the wire.** Nakama user ids are already public through `getUsers`. Exposing them to tablemates adds only the ability to follow status (above).
- **Friend codes as identifiers.** A shared code only allows sending a request, which the limits, decline and block cover. Enumerating 1.1e12 codes is impractical.
- **Generated codes spelling words.** They are screened with the server profanity list, which is never complete (the same stance as ADR-0001).
- **Protocol drift.** `PlayerInfo.userId` needs the projection and the decoder in step. Shared fixtures catch a dropped field.
- **Account deletion (future)** must also remove friend edges and the `social` records. Track it with the deletion work.
